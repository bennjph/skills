Readiness review for wip-presentation · 2026-04-21 · scope: repo truth, operating doctrine, and production-skill readiness

Presentation Capability System Readiness Check

This review checks how ready the repo is across the main verticals already present in the workspace: narrative, writing, design, prototype-first workflow, PPTX mechanics, vocabulary, evaluation, operating model, and skill-incubation doctrine.

The goal is not to say whether the final skill is ready to ship today. The goal is to show where the repo is already strong, where it is only directionally defined, and where exact schemas or catalogs are still missing.

Overall verdict: the repo is already strong on system shape, workflow logic, vocabulary, prototype-first direction, update logic, and evaluation framing. The main remaining work is not “what is this system?” anymore. It is exact schema work, catalog completion, and implementation of the repo operating layer such as AGENTS.md and session files.

Theme Readiness

1. Repo Boundary And System Shape

Strongly Defined

One presentation capability system, not multiple products. Human-in-the-loop by default. Final production skill is downstream from this repo, not the source of truth.

  • Well established in README.md, CONTEXT.md, and UBIQUITOUS_LANGUAGE.md.
  • Boundary with shared skills and machine-local config is also consistent with my-systems brownfield guidance.

2. Work Phases And Human Collaboration Flow

Strongly Defined

The repo has a stable six-phase operating flow: Briefing, Deck Archetype Comparison, Narrative Shaping, Prototyping, Authoring, Verification.

  • Deck Rehydration is clearly treated as part of Briefing for existing decks.
  • The system must collaborate with the human on the communication job, audience, thesis, evidence, slide plan, and contracts before PPTX authoring.

3. Narrative Architecture

Strongly Defined

Narrative is the strongest and most mature vertical in the repo. Decision framing, controlling idea, slide-role logic, skim-mode testing, and appendix discipline are all clearly stated.

  • Primary sources: narrative-architecture.md and 01-narrative-review.md.
  • The repo also already separates prompt-solvable narrative problems from deeper capability gaps.

4. Writing And Message Compression

Strongly Defined

Writing doctrine is clear and directly usable: point-first copy, action titles, low reader effort, strong note posture, and anti-filler rules.

  • Primary source: writing-style-guidelines.md.
  • Ready to inherit strongly into the repo’s future AGENTS.md.

5. Design Process And Taste

Partially Defined

The repo has strong taste rules and anti-slop guidance, but the actual reusable style asset model is not fully specified yet.

  • Strong on design intent in design-process.md.
  • Still partial on exact Style System package shape, style metadata, and the first real contents of the Style Pool.

6. Prototype-First Workflow

Strongly Defined

The repo is very clear that deck work should go through structured prototypes before PPTX. JSON and visual artifacts are upstream truth, not optional extras.

  • Primary sources: prototype-json-pipeline.md and PRESENTATION-OPERATING-STACK.md.
  • Prototype Tree is now a stable concept for branch-first visual comparison.

7. PPTX CRUD And Deck Engineering

Partially Defined

The conceptual CRUD model is strong, including editability, OOXML escalation, and update-safe verification. What is missing is real implementation and runtime proof.

  • Primary source: technical-crud-pptx.md.
  • Good doctrine exists, but no implemented authoring/update engine is present in the repo yet.

8. Existing Deck Adaptation And Rehydration

Strongly Defined

The repo is unusually strong here. Existing deck updates are first-class, and blind patching is explicitly rejected.

  • Existing Deck Adaptation and Deck Rehydration are canon terms with a defined minimum Rehydration Package.
  • This is ready as operating doctrine even if tooling is not yet built.

9. Deck Archetype Model

Partially Defined

The repo has a strong archetype concept and decision rule, plus a starter catalog. The open part is completeness and exact catalog design.

  • Starter archetypes exist in PRESENTATION-VOCABULARY-PACKAGE.md.
  • Still open: whether the current set is sufficient and what missing archetypes must be added during incubation.

10. Style System, Style Pool, Style Variant

Partially Defined

The logic is solid: shared style pool, select one system, create a light variant. The asset shape is still incomplete.

  • Strong rule clarity in CONTEXT.md and UBIQUITOUS_LANGUAGE.md.
  • Still missing: exact metadata for Style Fit Tags, file/package schema, and first v1 style library.

11. Presenter Voice System

Partially Defined

Presenter Voice, Voice Profile, and Voice Variant are named and placed correctly. The exact asset schema is still open.

  • The logic is stable: narrative first, then voice tuning.
  • Still missing: what a voice profile file contains and how voice should modify titles versus body copy versus speaker notes in an exact way.

12. Slide Role And Slide Contract Model

Partially Defined

The repo has a clear direction: small closed slide-role vocabulary, global contracts by role, variants by archetype. The exact final role list is still not frozen.

  • Good support from SLIDE-CONTRACT-TEMPLATE.md and the vocabulary package.
  • Still open: final role inventory and some fuzzy boundaries between insight, proof, recommendation, and comparison.

13. Evaluation, Verification, And Failure Diagnosis

Strongly Defined

This is one of the most complete product surfaces in the repo. Quality rubric, hard fail gates, validation order, and failure-mode diagnosis already exist.

  • Primary source: PRESENTATION-EVALUATION-SYSTEM.md.
  • Ready as doctrine. What remains is implementation of proof workflows and verify artifacts.

14. Repo Operating Model And AGENTS Doctrine

Partially Defined

The doctrine is now well defined in canon, but not yet instantiated as files. This is the clearest “defined but not built” area.

  • Strong decisions already exist for AGENTS.md, work/current.md, sessions/context.md, session chains, and doctrine split.
  • Still missing: the actual files themselves and the exact templates for the session surfaces.

Biggest Gaps To Close

Before The Repo Feels Operationally Complete

  • Create AGENTS.md from the stabilized doctrine.
  • Create work/current.md, sessions/context.md, and one dated session chain.
  • Write the short setup rationale so future agents understand why this repo uses the scaled model.

Before The Production Skill Is Actually Ready

  • Freeze the exact Slide Role list.
  • Define the real schemas for Style System and Voice Profile.
  • Decide whether the archetype catalog is complete enough.
  • Convert the readiness doctrine into a true production-skill gate.

Before Tooling Can Be Trusted

  • Build or prove the PPTX runtime path.
  • Create actual verification outputs, not only the evaluation doctrine.
  • Run experiments that validate style, voice, and update workflows against real deck cases.

Production Skill Readiness Call

Not Ready Yet

By the repo’s own rule, a production SKILL.md should wait until the key operating decisions are stable enough for reuse. The repo has now done a large share of that conceptual work, but a few readiness criteria are still only partial:

  • Strong enough already: domain language, work phases, human collaboration flow, deck rehydration, evaluation logic, prototype-first approach.
  • Still partial: archetype catalog completeness, style asset model, voice asset model, exact slide-role inventory, actual operating files, and executable proof.
Simple reading: the repo is ready to draft its operating layer now, but not yet ready to collapse into a fully authoritative production skill package.
